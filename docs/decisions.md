# Решения по проекту Gridlume

Зафиксировано 2026-10-28 по ответам владельца. Каждое решение можно пересмотреть —
тогда правим этот файл и пишем, что и почему изменилось.

## 1. Название, репозиторий, ветки

- **Название:** Gridlume (grid — сетка/инфраструктура, lume — свет: «всё видно»).
  Проверено 2026-10-28: на GitHub нет ни аккаунта, ни репозиториев с таким именем.
  Домены `gridlume.dev`, `gridlume.io`, `gridlume.ru` без DNS-записей (вероятно свободны), `gridlume.com` занят.
- **Репозиторий:** `github.com/metraveer/gridlume`, **приватный** до первой рабочей версии, потом публичный.
- **Ветки:** `main` — только проверенное; работа — в отдельных ветках (`design/mockup`, `feat/...`, `fix/...`), слияние через pull request.

## 2. Лицензия и монетизация

- **AGPL-3.0** для основного кода. Для дома и для всех, кто согласен с условиями AGPL, — бесплатно навсегда.
  AGPL требует, чтобы доработки, включая работу «как сервис», оставались открытыми, — это мешает
  кому-то взять проект и продавать закрытую версию.
- **Монетизация (позже):** двойное лицензирование — коммерческая лицензия для компаний, которым AGPL не подходит,
  плюс платные функции для бизнеса (SSO, расширенные роли, аудит, высокая доступность с PostgreSQL, поддержка).
- **Условие для двойной лицензии:** у проекта должны быть права на весь код. Перед тем как принимать чужие
  pull request'ы, подключаем соглашение участника (CLA). Пока пишем сами — не требуется.
- Отклонено: «source-available» лицензии (FSL, PolyForm Noncommercial) — не считаются открытыми и хуже
  воспринимаются сообществом; AGPL + коммерческая лицензия даёт тот же эффект открыто.

## 3. Пользователи и доступ

- Первая версия: **один администратор**. Модель ролей (владелец, администратор, наблюдатель) закладываем
  в базу сразу, интерфейс ролей — позже.
- **Доступ по умолчанию — только из своей сети или через VPN.**
- **Встроенный HTTPS без настройки:** при первом запуске ядро само создаёт сертификат для доступа по IP;
  если указать домен — само получает сертификат Let's Encrypt и продлевает его.
- **Двухфакторный вход (TOTP)** — обязателен, если ядро открыто в интернет; в своей сети — по желанию.

### Установка «без запар»

| Сценарий | Как |
|---|---|
| Разработка | `gridlume dev` — ядро и агент на этом компьютере, без TLS, перезапуск при изменениях |
| Попробовать и постоянно | одна команда установки (скрипт или Docker-образ) → в конце печатается **ссылка первого входа** `http://<адрес>:7420/setup#<код>` → открыть её, код подставится сам, создать владельца. Без ссылки экран подскажет, где её взять (`sudo gridlume setup-link`) |
| Рабочая установка | то же, плюс мастер подсказывает: VPN, домен и HTTPS, 2FA, резервные копии |

Одноразовый код первого входа защищает от того, чтобы администратора создал кто-то чужой, пока установка открыта.

### Первый вход (решение от 2026-10-28)

Владелец создаётся в браузере, как в других приложениях, но не «кто первый открыл — тот и владелец»: в окно между установкой и вашим входом владельцем мог бы стать любой в сети. Установщик печатает ссылку с одноразовым кодом после `#` (эта часть адреса не уходит на сервер и не попадает в журналы прокси); код подставляется сам, вводить его не нужно.

### Выпуски и обновления (решение от 2026-10-28)

- **Источник — релизы GitHub** публичного репозитория. Версии — семантические: следующая лежит в файле `VERSION`. Два канала, выбор в настройках приложения:
  - **стабильный** — выпуски `vX.Y.Z` (метка на `main`; после выпуска `VERSION` переходит к следующей);
  - **свежий** — каждое слияние в `main` после зелёного CI: предварительный выпуск `vX.Y.Z-dev.N`, где N — номер запуска CI.
- У каждой сборки свой выпуск, который больше не меняется; ядро находит последний через API GitHub и берёт все файлы из него. (Один «подвижный» выпуск не годится: GitHub минутами отдаёт закэшированные ссылки на файлы прежней сборки.) Хранятся пять последних свежих сборок.
- **Кто выпускает (решение от 2026-10-28).** Номер версии, название и описание выпуска выбирает и публикует ассистент сам, когда набрался осмысленный набор изменений; после стабильного выпуска `VERSION` переходит к следующей версии. Описание — на русском и английском, для человека: что изменилось для него. **Согласовать с владельцем заранее**, если выпуск опасный, непонятный или важный: необратимая миграция базы, изменения в самом механизме обновлений, агентах или установке на уже работающих машинах, несовместимые изменения API или настроек, версия 1.0 и другие крупные, ручные шаги на серверах, изменения, связанные с безопасностью.
- Обновление появляется в панели только после того, как CI собрал и проверил сборку. В панели: «Доступна версия …», что изменилось, кнопка «Обновить»; по желанию — автоматически.
- **Ручное обновление** — `sudo gridlume update` на машине. Это тот же механизм, что и кнопка: тот же релиз, та же проверка, поэтому одно не ломает другое.
- **Подпись:** CI подписывает список контрольных сумм ключом Ed25519; открытый ключ вшит в ядро и агента. Без верной подписи обновление не ставится.
- **Безопасно:** перед обновлением — копия базы; после — проверка, что ядро поднялось; если нет — возврат прежней версии и базы.
- **Права:** ядро работает под своим пользователем и не может заменить свой файл. Кнопка в панели только оставляет заявку; заменяет файл отдельная служба `gridlume-update` от root, которая сама скачивает и проверяет релиз.
- Агенты обновляются из ядра теми же подписанными сборками (этап 2г).

### Машина с ядром

Ядро ничего не собирает о своей машине: там тоже работает отдельный агент со своими правами (ядро смотрит в сеть, агенту нужен Docker — вместе это были бы права root у веб-сервера). Установщик ядра ставит и подключает местного агента сам, без кода. На схеме эта машина отмечена «здесь работает ядро».

## 4. Что показываем на схеме

**Узлы:** физический сервер, виртуальная машина, роутер/шлюз, подключение к интернету (провайдер),
облачный сервер (VPS), контейнер, сервис (сайт, база данных, бот), домен/DNS-запись, VPN-туннель,
хранилище (NAS, диск), умный дом (Home Assistant), прочие устройства (камера, принтер, телефон).

**Связи:** кабель/LAN, Wi-Fi, выход в интернет, VPN, «работает на» (контейнер → сервер),
«зависит от» (сайт → база), «указывает на» (домен → IP).

**Одна карта с уровнями** (решено 2026-10-28 после просмотра макета; вкладки «Сеть / Сервисы / Места» убраны как непонятные):
- **Верхний уровень — вся инфраструктура:** места цветными областями (деревня, дом, облако), в них машины и роутеры, сверху интернет; линии — сеть и VPN.
- **Вход внутрь машины:** двойной щелчок, кнопка «›» на узле или «Открыть внутри» в панели. Внутри — контейнеры и сервисы машины и линии «кто от кого зависит».
- **Пунктирные узлы внутри** — то, что снаружи машины, но с ней связано (например, домен, который указывает на сайт). Двойной щелчок по ним — переход туда, где они находятся.
- **«Хлебные крошки» сверху** показывают, где вы: «Вся инфраструктура / Облако · Timeweb / gridman.example». Щелчок по ним или Esc — уровень вверх.
- Дальше по тому же принципу можно будет зайти внутрь контейнера (процессы, порты, тома).

Раскладка автоматическая; перетащенный вручную узел запоминает место.

## 4а. Связи: скорость, состояние, события

Каждая связь на схеме живая. Три числа скорости, всегда рядом:

| Что | Откуда | Нагрузка на сервер |
|---|---|---|
| **Должна быть** — по договору или по порту | вносится руками (тариф 700 Мбит) + скорость порта, которую договорились сетевые карты (`1 Гбит`) | нулевая |
| **Идёт сейчас** — ↓ приём / ↑ передача | счётчики байтов сетевого интерфейса раз в секунду (агент, API роутера) | практически нулевая: чтение двух чисел |
| **Доступно на деле** — замер | короткий тест пропускной способности: по кнопке или по расписанию ночью | заметная, но короткая; поэтому никогда сам днём |

Плюс задержка и потери пакетов: маленькие ping раз в 10 секунд — незаметно для сети.

**Как показываем:**
- по линии бегут точки в сторону передачи; чем больше трафик — тем быстрее и гуще;
- на линии — подпись «идёт / должна быть», например `312 / 700 Мбит`; при отдалении схемы подпись прячется, остаётся толщина и цвет;
- **жёлтая** линия — загружена больше 80%, задержка выросла или есть потери; **красная** — связь пропала или потери больше 5%; проблемная линия мигает один раз и остаётся цветной, пока проблема есть;
- **наведение** — короткая сводка; **клик** — панель связи: все три скорости, график за час, задержка и потери, журнал событий этой связи и объяснение, что значит проблема и что сделать.

**У каждой линии есть смысл, а не только стрелка** (решено 2026-10-28):
- на линии — протокол и цифры: `HTTP · 42 запр/с`, `PostgreSQL · 118 запр/с`, `HTTPS`, `312 / 700 Мбит`;
- стрелка — кто к кому обращается;
- при наведении — что это и зачем одной фразой; по клику — панель: «Что это и зачем», «Как соединено» (тип, протокол и порт, кто к кому), скорость или запросы, «Если связь пропадёт», события;
- протокол и порт определяются автоматически (сети Docker, открытые порты, соединения); понятное описание подставляется по шаблонам для известных программ (PostgreSQL, nginx, Redis…), владелец может дописать своё.

**Правило:** всё, что тратит заметные ресурсы (замер скорости), запускается только по кнопке или по расписанию и объясняет, сколько это займёт.

## 6. Действия и безопасность

- **Версия 1 — только просмотр.** Управление (запуск/остановка, логи, терминал, перенос контейнера) — версия 2.
- **Каждое действие объясняется:** что произойдёт, что будет недоступно и сколько, можно ли отменить.
- **Уровни риска:** безопасно → осторожно → опасно. Опасные действия требуют ввести имя узла.
- **Журнал действий:** кто, что, когда, чем закончилось. Где возможно — кнопка отмены.
- **Перенос контейнера перетаскиванием** на другую машину: сначала план переноса и его последствия, потом подтверждение.
- Длинные объяснения — во всплывающих подсказках и панели «?», а не в основном интерфейсе.

## 7. Пароли

- **Своё зашифрованное хранилище:** мастер-пароль, Argon2id + XChaCha20-Poly1305, автоблокировка.

- В карточке узла пароль виден только после разблокировки хранилища; каждый просмотр пишется в журнал.

## 10. Агент

- Один файл + служба systemd, без Docker. Сначала Linux (amd64, arm64), Windows — позже.
- **Сам подключается к ядру** по зашифрованному соединению — работает за любым NAT, на машине не нужно открывать порты.
- **Подключение машины:** в интерфейсе «Добавить машину» → одна команда с одноразовым кодом → машина появляется на схеме.
- **Обновления:** ядро раздаёт подписанные сборки агента; автоматически или кнопкой в панели; при ошибке — откат.
- **Ключи:** при привязке агент создаёт пару ключей Ed25519 и отдаёт ядру только открытый. При каждом подключении он подписывает случайный вызов ядра. Утечка базы ядра не даёт подключиться от имени агента.
- **Связь:** WebSocket к ядру (`/api/agent/connect`). Снимок раз в 5 секунд; в базу пишутся минутные средние и максимумы. Метрики Linux агент читает сам из `/proc` и `/sys`, без gopsutil.

### Режимы прав агента (решение от 2026-10-28)

Доступ к Docker почти равен root: кто управляет Docker, может запустить контейнер с примонтированным `/`. Поэтому режим выбирается при установке, с объяснением, а в карточке узла видно, в каком режиме работает агент и каких данных из-за этого нет.

| Режим | Что видит | Риск при взломе агента | Кому |
|---|---|---|---|
| **Свой пользователь** `gridlume` в группе `docker` — **по умолчанию** | почти всё; SMART и чужие процессы — нет | через Docker — по сути вся машина; но сам процесс не root, служба systemd ограничена | большинству |
| **Только чтение**: свой пользователь, Docker только на чтение | метрики, контейнеры и их состояние | почти ничего, только смотреть | компаниям |
| **root** | всё | вся машина | дома, если не хочется думать |

**Docker и секреты (решение от 2026-10-28).** Агент только читает Docker API. Значения переменных окружения (там пароли и токены) с машины не уходят: агент отправляет лишь имена хостов, на которые они указывают, — этого хватает, чтобы предложить связь «api обращается к db». В режиме «только чтение» к Docker ходит прослойка `gridlume-docker-ro` от отдельного пользователя: она пропускает только чтение (без `archive`, `export`, `top`, `exec`) и вырезает значения переменных ещё до агента. Контейнеры становятся узлами внутри машины сами; связи между ними ядро только **предлагает**, а подтверждает человек.

Действия с контейнерами (этап 5) доступны только агенту с правом записи в Docker; в режиме «только чтение» кнопки неактивны и объясняют почему.

Так делают и другие: под root — Komodo Periphery, Portainer Agent, cAdvisor; свой пользователь в группе `docker` — Datadog, Beszel, Zabbix, Netdata.

## 11. Дизайн

- **Одна тема** — тёмная «ночная консоль»: на тёмном фоне лучше всего читаются цвета состояния. Светлая — возможна позже, токены это позволяют.
- **Без шаблонов «как у нейросети»:** никаких фиолетовых градиентов, стекла, эмодзи и карточек ради карточек.
  Цвет — только для смысла (состояние, выбор), всё остальное — оттенки графита.
- **Мало текста на экране:** подписи короткие, объяснения — в подсказках.
- **Телефон:** сначала только компьютер; токены и сетка готовы к адаптации, саму адаптацию делаем после рабочей версии.
- Дизайн-система — в коде: токены `web/src/design/tokens.css` и компоненты `web/src/design`. Первый макет хранится локально, в репозиторий не входит.

## 11а. Состав интерфейса (по макету от 2026-10-28)

- **«Что сломается, если…»** — у каждого узла: кто пострадает и от чего он зависит; подсветка на схеме, через уровни.
- **Путь запроса** — маршрут посетителя по шагам с задержкой каждого шага и подсказкой, где тормозит.
- **Строка состояния и центр проблем** — «Всё работает» / «Проблем: N»; переход к проблеме открывает её логи; отдельная вкладка «Советы».
- **Нижняя панель** — события всей инфраструктуры, живые логи выбранного узла (с фильтром ошибок), терминал машины, история за сутки с режимом «смотрю прошлое» (действия в нём недоступны).
- **Быстрые команды (Ctrl+K)** — переход и действия по тексту; риск и подтверждение те же, что в карточке.
- **Добавление** — агент одной командой, поиск устройств в сети (тип по производителю и портам), вручную; экран первого запуска из трёх шагов.
- **Состояния узла** — без сигнала (с временем последнего сигнала и подсказкой), сроки под узлом (сертификат, домен, баланс).
- **Карточка узла** — резервные копии (когда, размер, проверена ли восстановлением, расписание; «сделать», «проверить», «восстановить»), содержимое контейнера (порты и кто подключается, тома, настройки со скрытыми секретами, лимиты, процессы).
- **Экраны** — все узлы таблицей, журнал действий с откатом, хранилище паролей (просмотр и копирование пишутся в журнал), правила уведомлений простыми фразами и каналы, настройки.
- **Большая схема** — мини-карта, фильтр «только проблемы», сворачивание места в плитку.
- **Любое действие** проходит через одно подтверждение: что произойдёт, риск, для опасных — ввод имени, запись в журнал.
- **Что изменилось перед сбоем** — изменения за 30 минут до проблемы с пометкой «возможно связано» (не «причина»), «было / стало» и откат; ромбы изменений на шкале истории.
- **Заметки и история настроек** на каждом узле.
- **Без лишнего шума** — одна причина — одно сообщение, перепроверка перед тревогой (в том числе с другой машины), учёт зависимостей, сообщение о восстановлении.
- **Слои схемы:** присмотр (машины проверяют друг друга, облачный дежурный — всех снаружи; тревога придёт, даже если упадёт машина с ядром), питание (ИБП как узел, запас времени, выключение и включение по зависимостям), что видно из интернета (открытые порты, риски, проверка снаружи, «закрыть порт»).
- Подробности, почему выбраны именно эти функции: [`research/market-gaps.md`](research/market-gaps.md).
