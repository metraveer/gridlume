# Выпуски и обновления — как это устроено

Справочник на будущее: что где лежит, кто что делает, что может пойти не так и как это проверить.
Решения и их причины — в [`decisions.md`](decisions.md), раздел «Выпуски и обновления».

## Версии и каналы

| | Пример | Откуда берётся | Кому |
|---|---|---|---|
| **Стабильный** выпуск | `0.2.0` (метка `v0.2.0`) | метка на `main`, совпадающая с файлом `VERSION` | всем по умолчанию |
| **Свежая** сборка | `0.3.0-dev.9` (метка `v0.3.0-dev.9`) | каждое слияние в `main` после зелёного CI | тем, кто выбрал канал «Свежий» |

**«Свежий» включает и стабильные выпуски**: он берёт самый новый выпуск любого вида. Выйдет `0.3.0` после `0.3.0-dev.9` — «Свежий» предложит `0.3.0`, переключаться на «Стабильный» не нужно; следующая свежая сборка (`0.4.0-dev.N`) снова будет новее.

- `VERSION` — **следующая** версия. После стабильного выпуска её сразу поднимают (`0.2.0` → `0.3.0`), поэтому свежие сборки всегда новее последней стабильной.
- `N` в `-dev.N` и **номер сборки** (`build`) — номер запуска CI-процесса выпуска. Он растёт в обоих каналах, поэтому «новее» — это просто «номер сборки больше». Сравнивать строки версий не нужно.
- У каждой сборки свой выпуск на GitHub, который больше не меняется. Хранятся пять последних свежих сборок; стабильные — все.

## Что в выпуске

`gridlume-linux-{amd64,arm64}`, `gridlume-agent-linux-{amd64,arm64}`, `install-core.sh`, `release.json` (версия, канал, номер сборки, коммит, ссылка), `SHA256SUMS` и `SHA256SUMS.sig`.

**Подпись.** CI подписывает `SHA256SUMS` ключом Ed25519 из секрета `GRIDLUME_SIGNING_KEY`. Открытый ключ вшит в ядро (`internal/release/release.go`). Ядро не ставит файл, если подпись не сходится или контрольная сумма файла не совпадает с подписанной. Копия закрытого ключа должна лежать у владельца в KeePassXC: без неё новые выпуски не подписать, а установленные ядра их не примут.

## Как ядро узнаёт о новой версии

1. Раз в 6 часов (и по кнопке «Проверить сейчас») ядро спрашивает API GitHub про **оба** канала: `/releases/latest` для стабильного и список выпусков для свежего (берёт самый поздно опубликованный из `vX.Y.Z-dev.N` и `vX.Y.Z`).
2. Из найденного выпуска качает `SHA256SUMS`, подпись и `release.json`, проверяет подпись.
3. Панель показывает для каждого канала последнюю версию и её отношение к установленной: «установлена», «новее», «старше установленной», «выпусков пока нет», «нет связи с GitHub», «GitHub ограничил запросы» (без токена — 60 запросов в час, проверка раз в 6 часов укладывается с запасом).

**Выбранный канал** хранится в одном месте — файле `/var/lib/gridlume/update-channel`. Его пишут и панель (Настройки → Обновления), и установщик (`--channel`), его читает `sudo gridlume update`. Повторный запуск установщика без `--channel` оставляет выбранный канал.

## Как ставится обновление

```
Панель «Обновить»  ──► файл /var/lib/gridlume/update-request
                         │  (ядро работает под gridlume-core и не может заменить свой файл)
                         ▼
gridlume-update.path (systemd) замечает файл ──► gridlume-update.service (root):
   gridlume update --from-request
     1. сам находит выпуск и проверяет подпись (не доверяет ядру)
     2. копия базы: /var/lib/gridlume/backups/gridlume-<было>-<время>.db (от имени gridlume-core; хранятся пять последних)
     3. новый файл ядра рядом с /usr/local/bin/gridlume, старый — в gridlume.prev, затем замена одним переименованием
     4. сборки агента для установки на другие машины — в /var/lib/gridlume/agents
     5. systemctl restart gridlume и ожидание, что /api/version ответит новой версией (до 60 с)
     6а. получилось — обновляется и агент этой машины (gridlume-agent.prev сохраняется)
     6б. не получилось — возвращаются прежнее ядро и прежняя база, ядро запускается снова
     итог — в /var/lib/gridlume/update-status.json
```

`sudo gridlume update` в консоли делает то же самое тем же кодом. Есть `--check` (только посмотреть), `--channel stable|edge`, `--force` (поставить выпуск канала, даже если он не новее).

**На более старую версию не откатываемся автоматически**: если стоит свежая `0.3.0-dev.12`, а выбран стабильный канал с `0.2.0`, панель объясняет, что обновление придёт, когда стабильная станет новее. Старая версия может не понять базу новой.

## Что видит человек в панели

- **Версия, канал сборки, когда проверялось**.
- **Оба канала** с последними версиями; выбор канала — щелчком по нему.
- Для выбранного: «Доступна X» с кнопкой «Обновить», или «установлена последняя», или «установлена сборка новее канала».
- Если новее есть в другом канале — подсказка переключиться (со «Свежего» на «Стабильный» такого не бывает: стабильные выпуски приходят и в «Свежий»).
- **После обновления страница перезагружается сама**, чтобы загрузить новый интерфейс. Если открыто окно, идёт ввод или заполнена форма, она ждёт и показывает плашку, а перезагружается, как только это закончено.
- **Последний итог**, только если он относится к работающей версии: «Обновлено: A → B», «Установлено установщиком», «не запустилась, вернул A», «прервалось». Старые итоги не показываются.
- Если заявка ждёт дольше 2 минут — подсказка, что служба обновлений, похоже, выключена.
- После обновления открытая страница ещё работает со старым интерфейсом. Индикатор ядра раз в 15 секунд сверяет версию и, если она сменилась, предлагает обновить страницу.

## Установка и переустановка

```
curl -fsSL https://raw.githubusercontent.com/metraveer/gridlume/main/deploy/install-core.sh | sudo sh
```

Повторный запуск — это обновление с сохранением данных: ставит новые ядро и агента этой машины, оставляет выбранный канал и записывает «установлено установщиком», чтобы панель не показывала итог старого обновления.

## Файлы на машине

| Путь | Что | Владелец |
|---|---|---|
| `/usr/local/bin/gridlume`, `.prev` | ядро и прежнее ядро | root |
| `/usr/local/bin/gridlume-agent`, `.prev` | агент этой машины | root |
| `/etc/gridlume/gridlume.env` | адрес, папки, пользователь, `GRIDLUME_UPDATER=1` | root |
| `/var/lib/gridlume/gridlume.db` | база | gridlume-core |
| `/var/lib/gridlume/backups/` | копии базы перед обновлениями | gridlume-core |
| `/var/lib/gridlume/agents/` | сборки агента для других машин | root |
| `/var/lib/gridlume/update-channel` | выбранный канал | gridlume-core |
| `/var/lib/gridlume/update-request` | заявка на обновление (есть, пока не взята) | gridlume-core |
| `/var/lib/gridlume/update-status.json` | итог последнего обновления или установки | root |
| `gridlume.service`, `gridlume-update.path`, `gridlume-update.service` | службы | — |

## Если что-то не так

| Симптом | Где смотреть |
|---|---|
| «Обновить» нажато, ничего не происходит | `systemctl status gridlume-update.path`, `journalctl -u gridlume-update` |
| «Версия не запустилась, вернул прежнюю» | `journalctl -u gridlume -n 100` — почему не поднялась новая |
| «Подпись не сходится» | выпуск собран без верного ключа или подменён; ничего не ставить, проверить секрет и CI |
| «GitHub ограничил запросы» | подождать час; проверка повторится сама |
| Канал в панели и в консоли разный | `cat /var/lib/gridlume/update-channel` — источник один, этот |
| Всё сломалось совсем | `sudo cp /usr/local/bin/gridlume.prev /usr/local/bin/gridlume && sudo systemctl restart gridlume`; база — из `backups/` |

## Что ещё не сделано

- Агенты на **других** машинах пока не обновляются из ядра автоматически — это этап 2г. Сейчас их обновляет повторный запуск команды установки агента.
- Подпись сборки при самой **первой** установке проверяется только по контрольным суммам из HTTPS-ответа GitHub; все последующие обновления проверяют подпись.

## Как выпускать (для разработчика)

1. Свежие сборки выходят сами после каждого слияния в `main`.
2. Стабильный выпуск: `git tag -a vX.Y.Z <коммит на main> -m "Gridlume X.Y.Z" && git push origin vX.Y.Z` — метка должна совпадать с `VERSION`, иначе CI откажется. Затем описание выпуска на русском и английском (`gh release edit vX.Y.Z --notes-file ...`) и PR, поднимающий `VERSION` до следующей версии.
3. Кто и когда выпускает — правило в `decisions.md`: обычные выпуски — без согласования, опасные или важные — с владельцем.
